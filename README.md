# 갤럭시 스토어 위클리 출석체크 자동화 — 검토 기록 (철회)

## 목표

갤럭시 스토어의 "위클리 출석체크"를 매주 자동으로 눌러주는 시스템을 루팅 없이, 완전 무료로 만들어보려 했음.

## 검토한 방식

### 1. 서버/API 방식 (폰 없이 서버에서 삼성 계정 로그인 흉내내서 체크인 요청 전송)
- 장점: 폰 상태(전원/잠금)와 무관하게 동작, 지인 배포가 쉬움(스크립트 하나 공유)
- 단점:
  - Galaxy Store 앱은 SSL 인증서 피닝이 걸려있을 가능성이 높아, 통신을 들여다보려면 Frida 같은 후킹 도구가 필요하고 이는 사실상 루팅에 준하는 난이도
  - 여러 계정이 한 서버/IP에서, 정상 앱 서명·기기 인증 없이, 정해진 시각에 요청을 보내는 패턴은 리워드 어뷰징 탐지 시스템에 오히려 걸리기 쉬움
  - **결론: 더 어렵고 더 위험해서 폐기**

### 2. 온디바이스 UI 자동화 (Shizuku + Termux)
- 원리: 루팅 없이 "무선 디버깅" 페어링으로 Shizuku 앱에 ADB급 shell 권한을 위임받고, Termux에서 `rish`(Shizuku 연동 쉘)를 통해 `uiautomator dump`로 화면 구조를 읽고 `input tap`으로 실제 사람처럼 탭
- 장점: 실제 폰의 실제 세션으로 동작해서 서버 입장에서 사람이 누른 것과 구분 불가 → 계정 정지 리스크가 API 방식보다 훨씬 낮음. 비밀번호/토큰을 별도로 저장할 필요 없음
- 설계했던 세부 사항:
  - Termux/Termux:Boot는 반드시 **F-Droid나 GitHub Releases 중 같은 출처**로 설치 (플레이스토어 버전은 구버전+서명 불일치로 Termux:Boot이 깨짐)
  - Shizuku는 플레이스토어에서 "기기 호환 안 됨" 에러가 뜰 수 있어(일부 최신 Android 버전에서 등록판 미갱신 이슈), 이 경우 공식 GitHub(`RikkaApps/Shizuku`)에서 APK 직접 설치
  - 체크인 버튼 위치/진입 경로는 공개 문서가 없어 실기기에서 `adb shell uiautomator dump`로 직접 조사해야 함 (디스커버리 단계)
  - UI가 바뀌어도 쉽게 대응하도록, 좌표/resource-id를 `locators.conf`로 분리하고 폰에서 바로 재탐색 가능한 도우미 스크립트를 만드는 방향으로 설계
- **결정적 문제 (기술적 한계, 우회 불가):**
  - PIN/패턴/지문/얼굴 등 **진짜 보안 잠금이 걸려있는 상태**에서는, Shizuku/ADB의 shell 권한으로도 절대 뒤쪽 앱(갤럭시 스토어)에 탭 입력을 전달할 수 없음. 안드로이드 OS가 잠금화면이 떠 있는 동안은 그 뒤 앱에 입력 이벤트 자체를 아예 라우팅하지 않기 때문 — 루팅 없이는 넘을 수 없는 OS 레벨 보안 경계임
  - 즉 "폰이 잠겨있어도 100% 무인 자동화"를 하려면 잠금 화면 보안을 스와이프/없음으로 낮추는 것 외에는 방법이 없음
  - 절충안으로 "잠금 해제된 유휴 순간을 감지해서 그때만 자동 실행 + 수동 위젯 병행"도 검토했으나, 보안 잠금을 그대로 유지하면서 100% 무인 실행을 보장할 방법은 존재하지 않음

## 철회 사유

### 요구 조건의 충돌
사용자가 최종적으로 원한 조건은 다음 세 가지였음:
1. 루팅은 하지 않는다
2. 폰의 보안 잠금(PIN/패턴/지문/얼굴)은 그대로 유지한다
3. 폰이 잠겨있는 상태에서도 100% 자동으로 매주 출석체크가 실행되어야 한다

### 왜 셋을 동시에 만족할 수 없는가
안드로이드 OS는 보안 잠금화면(키가드)이 떠 있는 동안, 그 뒤에 있는 어떤 앱에도 입력 이벤트(탭, 스와이프 등)를 라우팅하지 않는다. 이는 원격제어·화면 미러링·매크로 등 어떤 소프트웨어적 방법으로도 우회할 수 없는 OS 레벨 보안 경계이며, Shizuku나 ADB로 얻는 "shell 권한"조차 이 경계 자체를 무시할 권한은 아니다(shell 권한도 결국 안드로이드 프레임워크의 입력 라우팅 규칙을 그대로 따름). 이 경계를 넘으려면 사실상 루팅(또는 그에 준하는 시스템 변조)이 필요한데, 이는 조건 1과 정면으로 충돌한다.

따라서 조건 2(보안 잠금 유지)와 조건 3(잠겨 있어도 100% 자동 실행)은 조건 1(루팅 안 함)을 지키는 한 동시에 성립할 수 없다. 즉 셋 중 하나는 반드시 포기해야 하는 구조적 트릴레마였음.

### 제시했던 대안과 최종 결정
- 보안 잠금을 스와이프/없음으로 낮추면 → 조건 3을 완전히 만족 가능 (조건 2 포기)
- 보안 잠금을 유지하고 "잠금 해제된 유휴 순간을 감지해 그때만 실행 + 수동 위젯 병행"으로 절충하면 → 대부분의 주에는 자동으로 되지만 100% 보장은 아님 (조건 3을 부분적으로만 만족)
- 위 두 절충 모두 받아들이지 않고, 세 조건을 전부 지키기를 원함 → 기술적으로 불가능하므로 **프로젝트 철회**를 선택함

즉 철회의 직접적 원인은 구현 난이도나 시간 부족이 아니라, **사용자가 요구한 세 조건이 안드로이드 OS의 보안 설계상 논리적으로 동시에 성립할 수 없었기 때문**임.

## 향후 재개 시 고려할 수 있는 선택지

- 보안 잠금을 스와이프/없음으로 낮추는 것을 받아들인다면 → Shizuku+Termux 온디바이스 자동화로 100% 구현 가능 (이 문서의 설계 재사용 가능)
- 보안은 유지하되 "거의 매주 자동, 가끔 놓칠 수 있음"을 받아들인다면 → 유휴 감지 + 수동 위젯 병행 방식으로 구현 가능
- 잠금 없는 보조 기기(예: 안 쓰는 여분 폰)를 하나 더 활용한다면 → 그 기기는 보안 포기 부담 없이 완전 자동화 가능
